## 1. 问题本质

这套 tools 的所有约束目前都是**文档级 / 提示词级**的：规则写得非常完整（`AGENTS.md`、`dir-graph.yaml`、各 `SKILL.md`、pipeline JSON），但规则的**执行者是模型本身**。

- 有平台时：平台做渐进加载（每节点重注入 CR 上下文）、pipeline 执行约束（编排器读 `passCondition`/`reviewLoop`）、受控 shell 适配器，规则被**代码强制**。
- 只有 IDE 时：没有这个强制层，规则退化为「模型自觉遵守」。长对话、上下文压缩、多轮接手后，模型会「读过就忘」，于是漂移。

**一句话：漂移的根因不是规则写得不好，而是规则缺少执行者。**

v2 补充一条推论：**代码化的过程本身会把规格里所有含混处逼出来**。今天靠模型「灵活理解」糊过去的状态机缺口、语义空白，一旦交给严格的代码执行者就会变成硬性死锁。所以落地前必须先做一遍规格完备性审计（见 §2.12 与 §5.7）。

## 2. 漂移点清单

### 2.1 ① CR-ID 与 status 指针丢失

- **约束位置**：状态机存在目标 workspace 的 `change-requests/_backlog.yml`（`dir-graph.yaml:210`）；`cr-status-set` 要求每次先读 `_backlog.yml` 再校验转换（`skills/cr/cr-status-set/SKILL.md:37-41`）。
- **IDE 中的漂移表现**：
  - 模型不会每轮真的 re-read `_backlog.yml`，而是凭对话记忆猜「现在应该在 developing」。对话变长或被压缩后，当前是哪个 CR、哪个 status 就模糊了。
  - `tech-design-review-pending` 这种「需结合 `review-annotations/sdd.yml` 的 verdict/blockers 才能决定下一步」的状态（`AGENTS.md:105`），模型容易直接跳到 approve 而不读评审证据。

### 2.2 ② 模型「口头宣布通过」，绕过状态写入

- **约束位置**：`README.md:27`「不是 prompt 里说'已经通过了'就算通过」；`README.md:548`「不得通过 prompt 文案隐式推进状态」；`README.md:529`「仅有 diff stat、commit log 或口头测试结论不足以通过质量门」。
- **IDE 中的漂移表现**：
  - 模型输出「代码评审通过 ✅，可进入下一步」，却没真正写 `review-annotations/code.yml` 的 `verdict=pass`、没写 `test-report.md`、也没调用 `approve-code` / `cr-status-set`。
  - pipeline JSON 里的 `reviewLoop`/`passCondition`（`pipeline-templates/code-implementation.pipeline.json:113-125, 174-189`）是给**平台编排器**读的机器约束。IDE 里没有编排器执行它们，模型只是「看着 JSON 假装遵守」。
  - 结果：状态机被口头推进，traceability、test-report、review annotations 出现空洞。

### 2.3 ③ git 脱离 controlled-shell

- **约束位置**：`skills/shared/controlled-shell/SKILL.md:19, 84-90` 白名单化 git 子命令并**禁止**输出「请在终端手工运行」；`AGENTS.md:124`、`README.md:553` 要求 git 必须走它。
- **IDE 中的漂移表现**：
  - controlled-shell 依赖 Tauri `runGit()` 或 opencode `session.shell` 适配器（`SKILL.md:54-60`），**这些适配器在纯 Codex/Claude/Cursor/Kimi 里不存在**。
  - 模型要么用 IDE 自由终端跑任意 git（违反白名单、可能污染主工作区而非 CR worktree，`README.md:554`），要么退回被明令禁止的「请在终端运行 git…」文本。两条都是漂移。
  - `push-progress` 要求覆盖 CR workspace 下**全部**参与仓库（`code-implementation.pipeline.json:135`），自由 git 下模型常只 commit 文档、忘了代码仓，checkpoint 残缺。

### 2.4 ④ 缺「知识库 + pipeline 执行约束层」这个地基

- **约束位置**：`README.md:11`（渐进加载、pipeline 执行约束）；`README.md:31, 33`（`specs/` + `delivery/` 是回写后的知识库）。
- **IDE 中的漂移表现**：
  - 没有知识库承接回写，`feature-writeback` 的产物（traceability.yml、specs、delivery）没有稳定落点，下一轮/下一个人接手时无从恢复上下文。
  - 没有 pipeline 执行约束层，`agent-skill-matrix.yml` 里的 owns/can-call/forbidden 边界（`AGENTS.md:59`）、node 顺序、reviewLoop replayNodes 全靠模型自觉，实际会跳节点、调用未授权 Skill、跳过 review-*/approve-*。

### 2.5 ⑤ 人工审批被模型代答（v2 新增，严重度与②同级）

- **约束位置**：`README.md:55`「人工审批人明确……不能由 prompt 隐式推进」；`README.md:199`「`human_approval` 只表示人工确认，不直接改状态」；`AGENTS.md:109`「涉及人工确认的节点，后续必须有明确的 `approve-*` 记录结论」。
- **IDE 中的漂移表现**：
  - ②治理的是「模型嘴上说通过、绕过写入」。⑤是另一条路径：模型**合法地**走完 `approve-requirement` / `approve-code` 的全部写入流程——证据文件齐全、gate 全过——只是 `human_approval` 环节根本没有人参与，是模型自己替人点了头。
  - IDE 里没有审批 UI，`human_approval` 节点天然退化为「模型自我确认」。这在需求审批、架构审批、开发启动、代码审批四个人工节点上都会发生。
  - **关键：证据 gate 校验不出「是否真有人类」。** v1 的 `crctl advance` 门禁对此完全无感，这是 v1 方案的结构性盲区。
- **治理方向**：`crctl approve` 做成交互式命令（见 §5.3）。

### 2.6 ⑥ 绕过 writeback 直接写 baseline（v2 新增）

- **约束位置**：`README.md:546` 第一条禁止事项「不得直接写 `specs/{id}/PRD.md` 或 `specs/{id}/SDD.md`；正式回写只能由 `writeback-prd-sdd` 执行」；`delivery/task/` 同理只归 `writeback-tasks`。
- **IDE 中的漂移表现**：
  - 模型「顺手」把改动直接写进 `specs/{id}/`、`delivery/task/`，跳过合并、回写、追溯链生成的完整编排，baseline 与实际代码、CR 过程产物失联。
  - v1 方案 §5.3 的 Write/Edit 拦截清单只覆盖状态文件（`_backlog.yml`、`cr.md`、`approval.yml`、`review-annotations/*.yml`），**没有覆盖 `specs/**` 和 `delivery/**`**，是 hook 清单的直接遗漏。

### 2.7 ⑦ 非 git 途径的写入漂移（v2 新增）

- **约束位置**：`README.md:554`「不得在主工作区代码目录直接编码；代码实现只写 CR worktree」。
- **IDE 中的漂移表现**：
  - 模型用 Write/Edit 工具或 `echo > file` 直接把代码写进主工作区，完全不经过 git——③的 git 拦截和状态文件拦截都管不到。
  - `echo x >> _backlog.yml`、`sed -i`、`mv`、`cp` 这类 Bash 写入同样能绕过只匹配 `\bgit\b` 的 Bash hook。
  - **结论：写路径围栏必须按「路径」拦（受保护路径 + 非 CR worktree 的代码目录），而不是只按工具和 git 命令拦。** 见 §5.4。

### 2.8 ⑧ review-loop 轮次计数漂移（v2 新增）

- **约束位置**：`AGENTS.md:144`「自动审查节点必须持久化 `review-loop.current-attempt` 与 `review-loop.attempts[]`；CR 类闭环还必须同步写入 `traceability.yml`，防止 `/resume` 后自修复轮次重置」；`README.md:215`「达到 `maxAttempts=3` 后仍未通过，pipeline 停止在当前闭环」。
- **IDE 中的漂移表现**：
  - 模型几乎必然忘记递增/持久化计数器。结果两个方向都坏：要么无限回修（maxAttempts 形同虚设），要么第一轮 block 后直接放弃闭环把问题丢给人工。
  - `/resume` 接手后计数器归零，自修复历史丢失。
- **治理方向**：计数器由 crctl 接管，不留给模型，也不等 P5 的完整 runner（见 §5.2 `crctl attempt`）。

### 2.9 ⑨ 产物 schema 漂移（v2 新增）

- **约束位置**：`AGENTS.md:122`「`SKILL.md` 必须明确输入、读取、写入、状态推进、失败处理」；`AGENTS.md:123`「写入型 Skill 必须说明如何调用 `validate-doc` 或等价校验」；`AGENTS.md:62` owner 三角色模型（每角色必含 `id` 与 `assigned-at`）；`AGENTS.md:111`「不得只修改顶层 `owner`」。
- **IDE 中的漂移表现**：
  - 即使模型老老实实写证据文件，长对话后**形状会走样**：字段名写错、verdict 枚举值超出范围、frontmatter 缺字段、`owners.{role}` 缺 `assigned-at`、只改顶层 `owner` 不改 `owners.{role}`、owner-history 不追加。
  - 本包为此专门设了 `validate-doc` Skill，但它同样是提示词级的——校验者也是模型，一起漂。
  - schema 漂移是**静默的**：写的时候不报错，直到下游读取或 gate 校验时才爆出来，且往往已经积累多轮。
- **治理方向**：`crctl validate` 把 validate-doc 代码化，覆盖全部受控产物（见 §5.2）。

### 2.10 ⑩ 元数据幻觉：时间戳与身份（v2 新增）

- **约束位置**：`assigned-at`、`updated-at`、`last-push-at`、`test-report.md` 的 tester 等字段遍布 owner 模型与 checkpoint 契约。
- **IDE 中的漂移表现**：模型会凭空编时间戳（尤其是日期，训练截止时间之后的日期错误率极高）和执行者身份，导致 owner-history、checkpoints[]、审批记录的时间线不可信，复盘与审计失效。
- **治理方向**：凡 crctl 写入的文件，时间戳与执行者一律由 crctl 生成，**拒绝模型作为参数传入**。成本极低，顺手消灭一整类漂移。

### 2.11 附加项 A：并发写 `_backlog.yml` 无锁

多人/多 agent 同时推进不同 CR 时，`_backlog.yml` 是共享单文件。平台原本兜了并发这层；IDE 单独使用时 crctl 需要 file-lock 或基于内容 hash 的 compare-and-swap（读时记 hash，写时校验 hash 未变，变了则重读重校验）。

### 2.12 附加项 B：落地风险——状态机规格缺口会变成死锁

代码化会把今天被模型「灵活理解」糊过去的规格缺口变成硬故障。一个现成的例子：

- `review-code` 通过后 status=`code-reviewing`（`dir-graph.yaml:225`）；
- 此时人工在代码审批环节**驳回**，pipeline 提示「开发者修复后重新执行代码编写与 review-code 节点」（`code-implementation.pipeline.json:199`）；
- 但 `dir-graph.yaml#transitions` 里**不存在 `code-reviewing → developing` 的转换**（只有 `developing → developing` 的 block 回路）。crctl 严格执行时，这条人工驳回路径会硬性卡死。

**落地 P1 前必须先对状态机做一遍「人工驳回路径」完备性审计**：四个 `human_approval` 节点各自驳回后，状态机是否存在合法回退转换。缺的先补进 `dir-graph.yaml`，再上代码执行者。

## 3. 核心原理：权威 / 判断 / 强制力 / 人类在环，四者分开

用代码替换提示词约束，必须先分清四件事（v2 在 v1 三分离基础上增加第四维）：

| 维度 | 能否代码化 | 说明 |
|---|---|---|
| **权威（authority）** | ✅ 能 | 「真正的状态」只能被代码改。模型再怎么口头宣布，只要权威状态只认代码写入，口头漂移就从「结构性错误」降级成「无害的废话」 |
| **判断（judgment）** | ❌ 不能 | 代码能查「证据是否存在、形状是否正确」，查不出「评审是否真的读懂 diff、测试报告是否属实」。这部分永远留给模型 |
| **强制力（enforcement）** | ⚠️ 分环境 | Claude Code 有 hooks → 可事前硬拦截；其余 IDE 靠「CLI 唯一合法路径 + gate 事后否决」；**最强的强制点在 agent 够不到的远端侧（CI / server-side hook），v2 将其列为正式组件**（见 §5.6） |
| **人类在环（human-in-the-loop）** | ✅ 能（v2 新增） | 「是否真有人类确认」可以代码化：交互式 TTY 确认、审批只认交互式写入。证据 gate 校验不出这一点，必须单独设防 |

> **关键思路：不要试图阻止模型「嘴上说通过」——那是 token 生成，代码管不住；而是让「真正的状态」只能被代码改，让「人工审批」只能被人类触发。**

## 5. 详细优化方案

### 5.1 总体架构：四个代码组件 + 分层强制

```text
┌──────────────────────────────────────────────────────────────┐
│  模型（IDE 中的 Codex/Claude/Cursor/Kimi/Qoder）               │
│  - 负责：判断、生成、叙述                                        │
│  - 不再拥有：直接改状态文件、自由跑 git、代答人工审批的权力       │
└───────────────┬──────────────────────────────────────────────┘
                │ 只能通过以下代码路径操作权威状态
                ▼
┌──────────────────────────────────────────────────────────────┐
│  组件 A: crctl —— 状态机 gate CLI（跨所有 IDE 通用，收益最大）    │
│    status / advance / gate / approve / validate / attempt      │
│    / test / next / git                                         │
├──────────────────────────────────────────────────────────────┤
│  组件 B: hooks —— 逃生口硬拦截 + 上下文自动重注入                │
│    · 拦裸 git、拦受控路径写入（含 specs/delivery/主工作区）      │
│    · SessionStart/PreCompact/UserPromptSubmit 注入 crctl status │
├──────────────────────────────────────────────────────────────┤
│  组件 C: pipeline-runner —— 按 JSON 驱动 + 校验 passCondition    │
├──────────────────────────────────────────────────────────────┤
│  组件 D: 远端侧校验 —— CI / server-side hook（v2 新增）          │
│    · 在 agent 够不到的地方校验状态转换与证据完整性                │
└───────────────┬──────────────────────────────────────────────┘
                ▼
┌──────────────────────────────────────────────────────────────┐
│  权威状态（唯一事实源，只被 crctl 写）                            │
│  _backlog.yml · cr.md · approval.yml · review-annotations/*     │
│  · test-report.md · traceability.yml · specs/ · delivery/       │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 组件 A：`crctl` —— 状态机 gate CLI

把 `cr-status-set` 从「模型执行的 Skill」变成「模型调用的代码」。跨所有 IDE 通用，直接治理 ①②③⑧⑨⑩。

**技术选型建议**：Node.js 单文件 CLI（本包 `skills/shared/engineering-docs/scripts/` 已用 TS/Node，生态一致；可编译为无依赖单文件便于各 IDE 调用）。

**设计原则（v2 修正 v1 的两处）**：

1. **门禁规则不硬编码，运行时解析事实源。** v1 把 passCondition 复刻进 crctl 内置规则，这违反 `AGENTS.md` 自身的单一事实源原则——以后改 pipeline JSON 不改 crctl（或反之），crctl 本身就成了新的漂移源。pipeline JSON 里的 `passCondition`/`reviewLoop` 本来就是机器可读的（`code-implementation.pipeline.json:113-125, 174-189`），`dir-graph.yaml#change-request-track.state_machine` 同理。**crctl 只实现解释器，不实现规则副本。**
2. **时间戳与身份由 crctl 生成。** `updated-at`、`assigned-at`、审批时间、attempt 时间线一律取系统时钟与配置身份，不接受模型传参（治理⑩）。

**子命令设计**：

| 子命令 | 行为（全部确定性代码） | 治理 |
|---|---|---|
| `crctl status <cr_id>` | 读 `_backlog.yml` + `dir-graph.yaml#state_machine`，输出 `CR-ID / status / 来源文件+hash / 合法下一步 trigger / 缺失产物清单` | ① |
| `crctl advance <cr_id> --to <status> --trigger <t>` | ①校验 `(current,next,trigger)` ∈ transitions[]（支持 wildcards）；②按 pipeline JSON 的 passCondition 校验产物存在且字段达标；③校验 attempts 链完整（⑧）；全过才写 `_backlog.yml` + `cr.md` frontmatter 并 commit（写前做 hash-CAS 防并发，§2.11），否则非零退出+结构化错误，**不写**。支持 `--embedded` 对应 `cr-status-set` 的 `commit_mode=embedded`（`merge-feature-branch`/`cr-archive` 需要状态与领域元数据同 commit） | ①②⑧ |
| `crctl gate <cr_id> --for <status>` | 只校验不写：返回 pass/block 与缺失项（供 runner 与人工预检） | ② |
| `crctl approve <cr_id> --stage <requirement\|tech-design\|dev-start\|code>` | **交互式命令**：终端 TTY 内展示证据摘要（评审 verdict、blockers、test-report status），要求人类按键确认并输入 approver 身份；确认后写 `approval.yml` 对应段并级联 `advance`。**非 TTY 环境（管道、脚本、模型直接调用）一律拒绝**。approval.yml 只认本命令写入 | ⑤ |
| `crctl validate <artifact-path>` | validate-doc 的代码化：按产物类型校验 schema——`cr.md`/`_backlog.yml` 的 owners 三角色（`id`+`assigned-at`）、owner-history 追加性、顶层 owner 兼容字段；`review-annotations/*.yml` 的 verdict 枚举与 blockers 结构；`test-report.md` 的 status/tester 字段；`traceability.yml` 各段结构 | ⑨ |
| `crctl attempt <cr_id> --loop <write-test-report\|review-code\|…>` | 计数器唯一写入点：递增并持久化 `review-loop.current-attempt` 与 `attempts[]`（同步 `traceability.yml`）；达到 maxAttempts 返回 `LOOP_EXHAUSTED`，`advance` 据此拒绝继续回修 | ⑧ |
| `crctl test <cr_id> --commands-from <tasks/TASK-NN.md \| plan.md>` | **自己执行**验证命令（lint/test/build），捕获原始 stdout/stderr 与退出码，生成 `test-report.md` 骨架（status 由退出码决定，tester 由配置身份决定）；模型只允许补充「分析」段落，不允许改 status | ②残留缩小 |
| `crctl next <cr_id>` | 读当前 status + 产物 + 评审证据，输出「下一个该跑的 node.ref 及其入参」；`review-annotations` 有未清 blocker 时**绝不**返回 `human_approval` | ④（防跳节点） |
| `crctl git <sub> [args] --cwd <path> --caller <skill-id>` | controlled-shell 的 IDE 实现。**按「子命令 + 形态 + 调用者」三元白名单放行**（v2 修正）：`SKILL.md:25-45` 的白名单本就是三元的，例如 `push` 只允许 `push -u origin <branch>` / `push origin <trunk>` / `push origin --delete <branch>` 三种形态，且各形态限定调用者。只校验子命令会放行 `git push origin main` 这类危险调用。越界返回 `FORBIDDEN_SUBCOMMAND`；同时过滤 `-c`/`--upload-pack` 等配置注入参数；每次调用打审计日志 | ③ |

**关于 v1「HMAC token 防手改兜底」的修正**：

v1 设计让 `crctl advance` 在状态 commit 附带 HMAC token，secret 存目标 workspace 本地配置。**这个威胁模型站不住**：模型在 IDE 里恰恰拥有本地文件读权限和 shell——它读得到 secret，就伪造得了 token。因此 v2 将其**诚实降级**：

- token 链保留，定位改为**防事故**（人手滑改文件、模型无意的裸 git 提交），不再宣称防 agent；
- 真正的强兜底换成**远端侧校验**（§5.6），执行点在 agent 够不到的地方。

### 5.3 人类在环：`crctl approve` 的交互式设计（治理⑤）

这是 v1 最大的结构性盲区：证据 gate 校验不出「是否真有人类」。设计要点：

1. **只有交互式 TTY 会话可以完成审批**。`crctl approve` 检测 stdin 是否为 TTY；非 TTY（模型经 Bash 工具调用、管道、CI）一律返回 `APPROVAL_REQUIRES_HUMAN` 并拒绝写入。
2. **审批前强制展示证据摘要**：评审 verdict/blockers、test-report status、attempt 历史，人类看着证据按键，而不是盲目 y/N。
3. **approval.yml 的四个段（requirement / tech-design / development-start / code）只认 `crctl approve` 写入**；hook 环境下直接 deny 模型对 `approval.yml` 的 Write/Edit；无 hook 环境靠远端侧校验兜底。
4. 在 Claude Code 里，模型调用 `crctl approve` 会触发权限确认提示，天然形成第二道人类在环。
5. **P1–P4 过渡期语义**：在完整 runner（P5）落地前，`human_approval` 节点的执行语义就是「人类在终端跑 `crctl approve`」——这同时解决了 v1 未交代的 runner-less 阶段 human_approval 如何落地的问题。

**残留**：人类本身敷衍点头，代码管不了——这是流程对人的要求，不是工具问题。

### 5.4 组件 B：hooks —— 写路径围栏 + 逃生口硬拦截（治理③⑥⑦）

**Claude Code（能力最强，事前硬拦截）**，在目标 workspace 的 `.claude/settings.json` 配置：

- `PreToolUse` on `Bash`：
  - 匹配 `\bgit\b` 且非 `crctl git …` 形式 → `deny`，提示改用 `crctl git`；
  - **（v2 新增）匹配对受保护路径的重定向/原地写入**（`>`、`>>`、`sed -i`、`tee`、`mv`、`cp` 目标命中受保护路径）→ `deny`。裸 Bash 写入是 v1 hook 清单的盲区。
- `PreToolUse` on `Write`/`Edit`，受保护路径清单（v2 扩展）：
  - v1 已有：`change-requests/**/_backlog.yml`、`**/cr.md`、`**/approval.yml`、`**/review-annotations/*.yml`；
  - **v2 新增**：`specs/**`（只归 `writeback-prd-sdd`，治理⑥）、`delivery/**`（只归 `writeback-tasks`，治理⑥）、`**/test-report.md`（只归 `crctl test` 骨架 + 模型补分析段）、以及**主工作区代码目录**（代码只准写 CR worktree，治理⑦——worktree 根从目标 workspace `dir-graph.yaml#repositories` 解析）。

**上下文自动重注入（v2 新增，直接削掉①的最大残留）**：

- `SessionStart` / `PreCompact` / `UserPromptSubmit` hook 把 `crctl status <active-cr>` 的输出注入上下文（additionalContext）。
- 效果：模型**每轮**看到权威指针（当前 CR、status、合法下一步、缺失产物），不再依赖「模型选择去调用」的自觉。这是对平台「渐进加载」最便宜的等价替代。

**其余 IDE（Codex/Kimi/Cursor/Qoder，降级策略）**：

- 若该 IDE 提供 hook/tool-gate 机制 → 等价配置（Cursor 已有 hooks beta，能力以实测为准）。
- 若没有 → 依赖「crctl 唯一合法路径 + gate 事后否决 + 远端侧校验（§5.6）」；同时在 workspace 的 `AGENTS.md` 顶部加一段「本环境无 hook，git 一律走 `crctl git`，审批一律走 `crctl approve`」的醒目约束（提示词兜底，最后一道）。

### 5.5 组件 C：`pipeline-runner` —— 按 JSON 驱动（治理④）

把 pipeline JSON 从「模型阅读的说明」变成「代码执行的脚本」。

- 读 `pipeline-templates/{flow}.pipeline.json`，按 `nodes[]` 顺序推进。
- 每个 `kind:skill` 节点执行后，调用 `crctl gate` 校验该节点声明的产物。
- 遇到含 `reviewLoop` 的节点：`passCondition` 不满足时，严格按 `replayNodes[]` 顺序回修，轮次经 `crctl attempt` 记账，`maxAttempts` 用尽才停；**blocker 未清空绝不进入 `human_approval`**。
- `human_approval` 节点：runner 暂停，等待人类完成 `crctl approve`（§5.3），随后由显式 `approve-*` 节点级联写状态——runner 自己不推进（对齐 `AGENTS.md:109`）。

**最小可用形态**：先不做全自动 runner，`crctl next`（§5.2）已能挡住「跳节点」，实现成本远低于全量 runner。

### 5.6 组件 D：远端侧校验 —— agent 够不到的强制点（v2 新增）

这套流程本来就把 checkpoint 推到 `origin/requirement/{CR-ID}`（push-progress 契约），天然具备远端侧校验的挂载点：

- 在 CI（或 server-side pre-receive hook）上对 `requirement/*` 分支跑校验作业：
  - 状态 commit 的 `(from, to, trigger)` 是否 ∈ `dir-graph.yaml#state_machine.transitions[]`；
  - 状态推进 commit 是否携带对应证据文件（review-annotations、test-report、approval.yml）且 `crctl validate` 通过；
  - `merge-feature-branch` 前置校验：目标 CR 必须 `code-approved` 且证据链完整，否则 CI 红灯阻断合入 trunk。
- **这是无 hook IDE 的真正等价强制层**：本地怎么漂，漂移产物到不了 trunk 和 baseline。相比 v1 的本地 HMAC token（agent 读得到 secret），远端校验的执行点在 agent 权限边界之外。
- 实现上直接复用 crctl：CI 里跑 `crctl gate` / `crctl validate` 即可，不需要第二套校验代码。

### 5.7 前置任务：状态机完备性审计（v2 新增，P1 的硬前置）

按 §2.12，代码化前先审计并修补 `dir-graph.yaml#transitions`：

1. 枚举四个 `human_approval` 节点（需求审批、架构审批、开发启动、代码审批）的**驳回路径**，确认各自存在合法回退转换。已知缺口：`code-reviewing → developing`（人工驳回代码审批后无法回到 implement-code）。
2. 核对每个 pipeline 节点 prompt 里描述的状态变化都能在 transitions[] 中找到对应条目。
3. 修补方式：更新 `dir-graph.yaml`（唯一事实源），同步 `AGENTS.md` 状态链路说明与 README 状态机图。

### 5.8 知识库落点

pipeline 执行约束层需要稳定的回写落点。在目标 workspace 固定：

- `specs/{id}/`：回写后的 PRD/SDD baseline（只由 `writeback-prd-sdd` 写）。
- `delivery/task/`：回写后的任务（只由 `writeback-tasks` 写）。
- `traceability.yml`：需求↔设计↔任务↔测试↔代码提交的追溯链。

`crctl advance → archived` 前校验以上落点已生成，未生成则否决——把「知识库有没有真正沉淀」也变成代码门禁。

## 7. 诚实的边界（永远留给模型 + 提示词 + 人）

1. **证据的真伪与质量**：代码能查 `code.yml` 有没有 `verdict=pass`、diff range 是否非空；查不出「评审是否真读懂 diff」。`crctl test` 代执行验证命令能把「测试结论造假」这一块实质性缩小，但「评审质量」到不了 100%。
2. **口头 prose 本身**：模型仍会输出「✅ 已通过」。代码不 gag 它，只让它**不算数**。
3. **人类审批的质量**：`crctl approve` 保证「有人按了键」，保证不了「人认真看了」。这是流程对人的要求。
4. **跨 IDE 强度不均**：Claude Code 能事前硬拦截；其余 IDE 是「CLI 唯一合法路径 + gate 事后否决 + 远端侧校验」。本地 HMAC token 只防事故、不防 agent（secret 在 agent 可读范围内）——v2 不再把它当安全边界宣传。
5. **Actor 身份自报**：`agent-skill-matrix.yml` 的 owns/can-call/forbidden 边界需要知道「当前 Actor 是谁」，而 IDE 中这只能由模型自报（`--caller` 参数）。代码能校验「该 caller 是否有权」，校验不了「自报的 caller 是否属实」。远端侧只能核到推送者身份粒度。

## 8. 验收标准（v2 扩展）

治理生效的可验证信号：

**v1 保留项**
- [ ] 任意时刻 `crctl status <cr>` 输出的 status 与 `_backlog.yml` 完全一致，模型不再自报 status。
- [ ] 缺失 `code.yml.verdict=pass` 或 `test-report.status=pass` 时执行 `crctl advance --to code-approved` **必定非零退出且不写文件**。
- [ ] Claude Code 环境下，`git commit` 直接调用被 hook deny，只有 `crctl git` 放行。
- [ ] `crctl next` 在 `review-annotations` 有未清 blocker 时，绝不返回 `human_approval` 作为下一步。
- [ ] `crctl advance --to archived` 在 `specs/`/`delivery/`/`traceability.yml` 未生成时否决。

**v2 新增项**
- [ ] 模型经非 TTY 通道调用 `crctl approve` 必定返回 `APPROVAL_REQUIRES_HUMAN` 且不写 `approval.yml`（⑤）。
- [ ] Claude Code 环境下，直接 Write `specs/{id}/PRD.md`、`delivery/task/*`、`approval.yml`、主工作区代码目录均被 deny；`echo >> _backlog.yml` 等 Bash 重定向同样被 deny（⑥⑦）。
- [ ] `/resume` 接手后 `review-loop.attempts[]` 不重置；达到 `maxAttempts` 后 `crctl advance` 拒绝继续回修并输出 `LOOP_EXHAUSTED`（⑧）。
- [ ] 手工构造字段名错误 / verdict 枚举越界 / owners 缺 `assigned-at` 的产物，`crctl validate` 必定报错定位到字段（⑨）。
- [ ] crctl 写入的所有时间戳与系统时钟一致，传入伪造时间戳参数被拒绝（⑩）。
- [ ] `git push origin <trunk>` 之外形态的 push 经 `crctl git` 调用被 `FORBIDDEN_SUBCOMMAND` 拒绝（三元白名单生效，③）。
- [ ] 远端 CI 对携带非法状态转换或缺失证据的 `requirement/*` 分支推送亮红灯，`merge-feature-branch` 无法合入 trunk（组件 D）。
- [ ] 修改 pipeline JSON 的 `passCondition` 后，`crctl gate` 行为随之变化而**无需改 crctl 代码**（单一事实源验证）。
- [ ] P0 审计后，四个 `human_approval` 节点的驳回路径均存在合法状态转换，`crctl advance` 可走通（附加项 B）。

## 附：与现有约束的关系

本方案**基本不改动**现有 Skill / Pipeline / `_index.yml` / `agent-skill-matrix.yml` 的契约，是在其之上补一个**执行强制层**：

- `crctl advance` 是 `cr-status-set`（`skills/cr/cr-status-set/SKILL.md`）的代码化执行器，含 `--embedded` 对应其 `commit_mode=embedded`。
- `crctl git` 是 `controlled-shell`（`skills/shared/controlled-shell/SKILL.md`）在 IDE 环境的运行时适配器实现（对应其「运行时适配要求」）。
- `crctl validate` 是 `validate-doc` 的代码化执行器。
- `pipeline-runner` 与 `crctl gate` 执行的就是 `pipeline-templates/*.pipeline.json` 里的 `passCondition`/`reviewLoop`，不新增编排语义，只强制其被真实执行。

**两处必要的文档同步（v1「零改动」说法的例外）**：

1. `controlled-shell/SKILL.md` 的适配器优先级表需登记 crctl 为正式适配器（新增一行环境：纯 IDE → 首选 `crctl git`），否则该 SKILL 的环境表与实际运行方式脱节。
2. `dir-graph.yaml#transitions` 需按 P0 审计结果补人工驳回回退转换（如 `code-reviewing → developing`），并同步 `AGENTS.md` 与 README 状态机说明。

即：**把已有的提示词契约，配一个代码执行者；把规格里被这个执行者逼出来的缺口，先补上。**
