AI First 研发协同平台
phase0 Tools 包全解

一套把「产品规划 → 需求 → 架构 → 编码 → 质量审查 → 回写归档」全链路结构化的预置能力包。它让 AI 参与一条可追踪、可恢复、可审计的研发流水线，核心是把每一次产品变更沉淀为一个 CR（Change Request）工作容器。

9 个预置 Agent 45+ 个 active Skill · 9 大 domain 8 条 active Pipeline 13 态 CR 状态机 事实源驱动 · YAML/JSON 声明式

§0平台定位与核心思想

这是一个预置到内部研发协同平台的可用版本 tools 包，而不是业务项目工作区。它维护的是「可安装到目标 workspace」的 Agent、Skill、Pipeline 模板与流程手册。

整套 tools 覆盖软件产品研发从产品规划到代码实现再到知识回写的完整流程，既可个人独立使用，也可团队协作推进；并且可以按 Skill / Agent / Pipeline 等不同颗粒度单独拆出来使用。

⚠ 一个关键前提 这套 tools 单独放在 Codex / Claude / Cursor / Kimi 等工具上使用时容易出现「飘移」。作者自己是结合平台本身（渐进加载、pipeline 执行约束等执行层优化）+ 配套知识库一起使用的。官方建议不是照抄内容，而是把「核心思路」落地到团队：想清楚两件事 ——「①团队的所有信息/资产如何管理」「②团队基于什么协作、如何协作」。

唯一事实源与读取顺序

平台采用严格的「单一事实源（Single Source of Truth）」设计。所有 AI Agent 在动手前必须按固定顺序读取入口文件，不同入口之间不允许维护互相冲突的规则：

§1CR：贯穿全程的工作容器

整个平台最关键的设计不是某个 Skill 写得多完整，而是把一次产品变更变成一个可持续推进、可多人接手、可被 AI 稳定理解的 CR（Change Request）。

之所以选 CR 而不是传统 issue 模式，核心原因是要把所有执行过程完整沉淀下来，作为后续复盘的信息来源，并且能与代码保持强一致。每个 CR 都有自己的目录、分支、worktree、状态、owner 和过程产物。

可恢复

PRD、SDD、任务拆解、测试报告、评审意见、审批记录、traceability 全部沉淀在 change-requests/{CR-ID}/。换人、换机、换 Agent 都能从 CR 本身恢复上下文。

可追踪

CR 通过状态机往前走。不是 prompt 说「通过了」就算通过，每个关键节点都要由明确的 Skill 写入证据并推进状态。

可审计

三角色 owner（需求/开发/测试）显式化责任归属；Agent 之间通过权限矩阵限定边界，谁能做什么一目了然。

三角色 Owner 模型

CR 责任归属以 cr.md 与 _backlog.yml 的 owners 为准。顶层 owner 仅作旧视图兼容，默认等于 owners.requirement.id。

owners:
  requirement:              # 需求负责人：PRD、需求评审、需求审批
    id: product-owner
    assigned-at: "2026-07-18T10:00:00+08:00"
  development:              # 开发负责人：SDD、任务拆分、编码、代码审批
    id: dev-owner
    assigned-at: "2026-07-18T10:00:00+08:00"
  test:                     # 测试负责人：验证证据、测试报告
    id: test-owner
    assigned-at: "2026-07-18T10:00:00+08:00"
角色变更必须通过 handover-cr 或 resume-from-remote 的移交逻辑更新 owners.{role}.id 与 assigned-at，并追加 owner-history。不得只改顶层 owner。

过程工作台 → 团队知识库

CR 的过程产物不会一直停留在临时目录。开发完成并通过审批后，feature-writeback 会把分支合回各仓 trunk，把产物写入 baseline。所以：CR 是过程工作台，specs/ 和 delivery/ 是回写后的团队知识库。

§2整体架构：四层能力模型

tools 包由四类核心资产构成，通过 _index.yml 台账注册、由 agent-skill-matrix.yml 约束边界、由 Pipeline JSON 编排执行。

目录结构

所有相对路径默认以 tools/ 为根。目录本身极简，全部能力通过台账文件登记：

tools/
├─ AGENTS.md                 # ① 所有 AI 工具共享的行为约束入口
├─ CLAUDE.MD                 #   Claude 专用入口，只转发到 AGENTS.md
├─ dir-graph.yaml            # ② 目录图与事实源声明 + CR 状态机
├─ agent-skill-matrix.yml    # ③ Agent/Skill 权限矩阵（机器可读）
├─ AGENT-SKILL-MATRIX.md      #   权限矩阵人读说明
├─ README.md                 # ④ 完整使用流程、流程图、节点说明
├─ agents/                   # 预置 Agent 定义 + _index.yml 台账
│   ├─ _index.yml
│   └─ {agent-id}.md
├─ skills/                   # 预置 Skill 定义 + _index.yml 台账
│   ├─ _index.yml
│   └─ {domain}/{skill-id}/SKILL.md
└─ pipeline-templates/       # Pipeline JSON 模板 + _index.yml 台账
    ├─ _index.yml
    └─ {flow}.pipeline.json
目标 workspace 与 tools 包的边界：tools 包安装到目标 workspace 的 tools/ 下后，Skill 运行时读取的是目标 workspace 的 change-requests/、specs/、delivery/、docs/、constraints/ —— 这些不是 tools 包内目录。仓库/trunk/worktree 一律由目标 workspace 的 dir-graph.yaml#repositories 动态解析，禁止写死本机路径或固定仓库名。

Agent 智能代理系统

Agent 是调度入口，只负责路由、编排和质量判断。设计上分三种模式：primary 可承接完整阶段、subagent 提供子能力、system 系统编排器（非可部署 Agent）。

Agent 设计理念：路由 ≠ 执行

每个 Agent 文档都带 constraints 约束段，明确「不做什么」。以 dev-agent 为例，它的红线是：

  • 不得直接写入 specs/，正式回写仅由 writeback-prd-sdd 执行；
  • 不得手动编辑 _backlog.yml，状态推进必须经 develop/* 封装 Skill 间接完成；
  • 不得在主工作区代码目录直接编码，实现只写 CR worktree；
  • 评审有 blocker 时必须回到对应修复节点自修复，完整通过后才可进入 human_approval。

Skill 技能系统

Skill 是平台的能力原子，每个对应一种文档、流程节点或工具能力，按 domain 组织为 skills/{domain}/{skill-id}/SKILL.md。每个 active Skill 在矩阵中必须且只能有一个 owns owner。

三个特殊的 shared Skill

🛡 controlled-shell

受控 shell 执行规范：给 requirement/sync 组 Skill 提供白名单化 git 命令入口，禁止「手工指引文本」回退。所有 git 操作的唯一合法通道。

📐 engineering-docs

按模板生成/校验 PRD·SDD·MODULE·PLAN·TASK·FORM·RELEASE 的 frontmatter + 正文骨架，已去 MCP 化，Agent 按步骤执行。

✅ validate-doc

通用文档校验，所有写入型 Skill 自动调用，保证产物结构合规。

权限矩阵：谁能调用什么

agent-skill-matrix.yml 用四种关系约束调用边界。执行时先按 Pipeline owner 选入口，再按矩阵判断该入口能否调用某 Skill。

关系含义执行规则
owns主责维护与默认执行每个 active Skill 有且仅有一个 owner；新增 Skill 必须先补矩阵
can-call职责边界内可协作调用不得绕过 Skill 自身前置条件、状态机和质量门
external目标运行时提供的外部方法论 Skillphase0 不打包同名 SKILL.md，只声明依赖（如 brainstorming、executing-plans）
forbidden明确禁止调用手工演练与系统编排都不得调用；改边界需先修矩阵
示例：quality-reviewer-agent 可 can-call 所有 review-* 质量门，但 forbidden 所有 approve-* 与 cr-status-set —— 它能审，但不能批、不能推进状态。dev-agent forbidden writeback-prd-sdd 与 merge-feature-branch —— 开发不碰回写与合并，这些归 system-orchestrator。

所有自动审查节点都必须先完成自修复闭环、完整通过 Review 后才可进入下一环节（含人工审核）。发现 blocker 时不丢给人工兜底，而是带着 review_feedback 回到对应修复节点，最多 3 轮。

数据与事实源流转

每个阶段的工作区产物在回写后转为 baseline/归档产物。这是「过程工作台 → 团队知识库」的物理落点映射。

§5最佳实践路径推荐
