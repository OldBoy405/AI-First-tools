1. 项目整体架构分析

1.0 架构总览

AI First 研发协同平台 Phase0 Tools 包是一个纯声明式的预置工具包，可安装到目标 workspace 的 tools/ 目录下。它通过 Agent（智能代理）→ Skill（原子能力）→ Pipeline（编排流程） 三层架构，将软件研发全生命周期中的每一个步骤都变成结构化、可追踪、可审计的事实。

🏗️ 三层架构：Pipeline（编排"何时做"）→ Agent（决定"谁来做"）→ Skill（定义"怎么做"）。每一层都有明确的契约文件（JSON/YAML/Markdown），保证机器可解析、人可阅读。

1.2 智能代理系统 (Agents) 详解

Agent 是调度与编排入口，负责路由、质量判断和状态推进。Agent 不绕过 Skill 直接写受控状态文件，所有写入操作必须通过 Skill 完成。

1.3 技能系统 (Skills) 详解

Skill 是平台的最小能力单元，每个 Skill 以 SKILL.md 文件定义，必须包含 name: frontmatter，并明确输入、读取、写入、状态推进、失败处理。

⚡ Skill 设计规范：
• 每个 SKILL.md 必须有 name: frontmatter
• 写入型 Skill 必须说明如何调用 validate-doc 或等价校验
• 涉及 git/shell 的 Skill 必须通过 controlled-shell 约束命令范围
• 每个 active Skill 在 agent-skill-matrix.yml 中有且只有一个 owns owner

1.4 流水线模板 (Pipeline Templates) 详解

Pipeline 节点类型

🔧 Skill 节点

调用 active Skill 执行具体操作。包含 ref（Skill ID）、onFail（abort/skip）策略和超时设置。

👤 Human Approval 节点

需要人工确认。审批后由显式 approve Skill 推进状态，而非隐式通过。最长等待时间可达 2880 分钟。

💻 Code Generation 节点

调用外部 coding runtime（Claude Code/Cursor/Codex）执行代码生成，支持子 Agent 和 TDD 模式。

🔄 reviewLoop 自修复

自动审查节点声明 reviewLoop，blocker 未清空时自动回到修复节点。最多 3 次自修复尝试，每次持久化轮次记录。

1.5 Agent-Skill 权限矩阵

agent-skill-matrix.yml 是 Agent 与 Skill 关系的机器可读事实源，定义四种关系类型：

关系含义约束
owns 主责维护与默认执行 每个 active Skill 必须且只能有一个 owner
can-call 可在职责边界内调用 不代表主责，调用时仍需遵守 Skill 前置条件
external 目标运行时提供的外部方法论 Skill phase0 tools 不打包同名 SKILL.md，只声明依赖
forbidden 明确禁止调用 防止跨域越权或跳过流程

2. 在 Cursor 与 Claude Code 中的使用方法

2.1 环境配置

📋 使用前提：
1. workspace 已初始化：AGENTS.md、dir-graph.yaml、change-requests/、specs/、delivery/、docs/
2. repositories 已声明：dir-graph.yaml#repositories 包含 knowledge-base repo、代码 repo、trunk、active 状态
3. 受控 shell 可用：git 操作走 controlled-shell 白名单适配器
4. Agent runtime 可用：代码实现阶段需要 Claude Code / Codex / Cursor 等外部 coding runtime
5. CR 角色 owner 明确：需求 owner、开发 owner、测试 owner 均已指定

2.2 安装 tools 包到目标 workspace

# 1. 将 phase0 tools 包克隆或复制到目标 workspace 的 tools/ 目录
git clone https://github.com/OldBoy405/AI-First-tools.git tools/

# 2. 验证文件完整性
node -e "const fs=require('fs');
for (const f of fs.readdirSync('tools/pipeline-templates').filter(f=>f.endsWith('.json')))
  JSON.parse(fs.readFileSync('tools/pipeline-templates/'+f,'utf8'));
console.log('json ok')"

# 3. 确保目标 workspace 的 dir-graph.yaml 正确声明了 repositories
# 关键字段: repositories[].id, repositories[].trunk, repositories[].active

2.3 在 Cursor 中使用

方式一：直接触发 Pipeline

在 Cursor 的 AI Chat 中直接输入触发命令，如 /requirement、/coding，Agent 会自动加载对应 Pipeline 并执行。

/requirement
title: 用户登录功能优化
summary: 重构登录流程，支持SSO和MFA
target_version: v2.1.0
requirement_owner: alice
dev_owner: bob
test_owner: charlie

方式二：单独调用 Skill

也可以直接调用单个 Skill 完成特定任务。在对话中描述需求，AI 会匹配对应的 Skill。

请使用 spec-query 帮我查找所有 v2.0.0 
版本的 baseline spec

方式三：Agent 自由对话

直接把 Agent 当作协作伙伴，Agent 会按 AGENTS.md 约束读取上下文、选择合适 Skill 执行。

我是需求负责人，请帮我评审 CR-2026-005 
的 PRD，并在通过后推进审批

2.4 在 Claude Code 中使用

Claude Code 通过 CLAUDE.MD 入口文件自动转发到 AGENTS.md，保证行为约束一致。

# CLAUDE.MD 内容（只做转发）
# 所有 AI 工具共享的行为约束入口在 AGENTS.md
# 详见 AGENTS.md 获取完整规则

Claude Code 特色能力

  • 通过 controlled-shell 安全执行 git 命令
  • 在 CR worktree 中进行代码编写（而非主工作区）
  • 自动读取 dir-graph.yaml 解析仓库路径
  • 遵守 agent-skill-matrix.yml 权限边界

典型启动方式

  • /requirement — 启动需求编写流程
  • /architecture CR-2026-001 — 为指定 CR 编写架构设计
  • /coding CR-2026-001 — 进入代码实现阶段
  • /writeback CR-2026-001 — 回写并归档
  • /resume CR-2026-001 — 恢复在途 CR

2.5 Pipeline 执行示例 — 需求编写全流程

# Step 1: 在 Cursor / Claude Code 中触发
/requirement

# Step 2: 填写 Pipeline 输入参数
title: "启动面板多方案调研"
summary: "调研主流启动面板交互方案，选择最优方案并实现"
target_version: "v0.16.0"
source: "docs/product-planning/2026-07-01-q3-planning.md"
requirement_owner: "product-owner"
dev_owner: "dev-lead"
test_owner: "qa-lead"
auto_push_after_prd: true

# Step 3: Pipeline 自动执行
# → requirement-register: 创建 CR-2026-008，生成 worktree，写入三角色 owner
# → write-requirement-prd: 在 CR worktree 中生成 PRD.md
# → push-progress: 推送到远端 checkpoint

# → approve-requirement: 审批通过后推进 status=requirement-approved

# Step 4: 输出
# CR status: requirement-approved
# 下一步: /architecture CR-2026-008

3.2 CR 状态机 — 核心驱动引擎

整个研发流程通过 CR（Change Request）状态机 驱动。每个 CR 是一个工作容器，CR 目录包含 PRD、SDD、TASK、测试报告、评审证据、审批记录和 traceability。

stateDiagram-v2 [*] --> drafting: requirement-register drafting --> requirement_reviewing: review-requirement drafting --> drafting: review-requirement:block →\nwrite-requirement-prd requirement_reviewing --> requirement_reviewing: review-requirement requirement_reviewing --> requirement_approved: approve-requirement requirement_approved --> tech_designing: write-tech-design tech_designing --> tech_design_review_pending: write-tech-design complete tech_design_review_pending --> tech_designing: review-tech-design:block →\nwrite-tech-design tech_design_review_pending --> tech_design_reviewed: approve-tech-design tech_design_reviewed --> task_breakdown: write-dev-tasks task_breakdown --> developing: approve-dev-start developing --> developing: write-test-report:block →\nimplement-code developing --> developing: review-code:block →\nimplement-code developing --> code_reviewing: review-code pass code_reviewing --> code_approved: approve-code code_approved --> merging: merge-feature-branch merging --> writing_back: writeback-prd-sdd writing_back --> archived: cr-archive drafting --> rejected: cr-review-record:reject drafting --> withdrawn: cr-review-record:withdraw requirement_reviewing --> rejected: cr-review-record:reject requirement_reviewing --> withdrawn: cr-review-record:withdraw tech_designing --> rejected: cr-review-record:reject tech_designing --> withdrawn: cr-review-record:withdraw developing --> rejected: cr-review-record:reject developing --> withdrawn: cr-review-record:withdraw code_reviewing --> rejected: cr-review-record:reject code_reviewing --> withdrawn: cr-review-record:withdraw
🔑 关键设计：
  • human_approval 只表示人工确认，不直接改状态。所有状态推进必须由显式 Skill 完成
  • 自动审查发现 blocker 时，不把问题丢给人工兜底，而是带 review_feedback 回到修复节点自修复
  • 终态包括 archived、rejected、withdrawn 三种
  • CR 角色 owner 变更必须通过 handover-cr 或 resume-from-remote 的正式移交逻辑

3.4 自动审查自修复闭环机制

所有自动审查节点都具备自修复闭环能力，最多进行 3 次自动修复尝试。每次审查都持久化 review-loop.current-attempt 与 review-loop.attempts[]。

闭环评审节点修复节点通过条件最多尝试

4.5 禁止事项总结

⛔ 严格禁止：
  • 直接写 specs/{id}/PRD.md 或 specs/{id}/SDD.md — 正式回写只能由 writeback-prd-sdd 执行
  • 创建旧式单文件 spec 模型或把开发计划写进 specs baseline
  • 通过 prompt 文案隐式推进状态 — 必须由显式 Skill 完成状态变更
  • 调用未登记在 skills/_index.yml 的 Skill
  • 调用 agent-skill-matrix.yml 中当前 Actor forbidden 列表中的 Skill
  • 把 planning-draft 当作落盘 Skill — 落盘使用 write-planning-entry 或 write-planning-report
  • Agent 在终端自由执行 git — 所有 git 操作必须走 controlled-shell
  • 在主工作区代码目录直接编码 — 代码实现只写 CR worktree
  • 手工清理 CR worktree 或远端分支 — 成功归档后由 cr-archive 负责

4.6 CR 三角色 Owner 模型

🔑 角色变更规则：
• 必须通过 handover-cr 或 resume-from-remote 的角色移交逻辑
• 更新 owners.{role}.id、owners.{role}.assigned-at
• 追加 owner-history（记录 role/from/to/at/reason）
• 不得只修改顶层 owner 字段
