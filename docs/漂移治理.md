# 漂移治理 —— 用代码约束替代提示词约束

> 适用范围：本 phase0 tools 包在 Codex / Claude Code / Cursor / Kimi / Qoder 等 IDE 中**单独使用**（脱离原平台的渐进加载与 pipeline 执行约束层）时的漂移问题分析与治理方案。
>
> 依据：`README.md:11` 明确指出「本套 tools 如果只是在 Codex、Claude、qoder、Kimi 等工具上使用，比较容易出现飘移现象」，作者本人是结合「平台（渐进加载、pipeline 执行约束）+ 知识库」使用的。本文给出在缺少该平台时，用**代码执行层**等价替代的方案。

---

## 1. 问题本质

这套 tools 的所有约束目前都是**文档级 / 提示词级**的：规则写得非常完整（`AGENTS.md`、`dir-graph.yaml`、各 `SKILL.md`、pipeline JSON），但规则的**执行者是模型本身**。

- 有平台时：平台做渐进加载（每节点重注入 CR 上下文）、pipeline 执行约束（编排器读 `passCondition`/`reviewLoop`）、受控 shell 适配器，规则被**代码强制**。
- 只有 IDE 时：没有这个强制层，规则退化为「模型自觉遵守」。长对话、上下文压缩、多轮接手后，模型会「读过就忘」，于是漂移。

**一句话：漂移的根因不是规则写得不好，而是规则缺少执行者。**

---

## 2. 漂移点清单

### ① CR-ID 与 status 指针丢失

- **约束位置**：状态机存在目标 workspace 的 `change-requests/_backlog.yml`（`dir-graph.yaml:210`）；`cr-status-set` 要求每次先读 `_backlog.yml` 再校验转换（`skills/cr/cr-status-set/SKILL.md:37-41`）。
- **IDE 中的漂移表现**：
  - 模型不会每轮真的 re-read `_backlog.yml`，而是凭对话记忆猜「现在应该在 developing」。对话变长或被压缩后，当前是哪个 CR、哪个 status 就模糊了。
  - `tech-design-review-pending` 这种「需结合 `review-annotations/sdd.yml` 的 verdict/blockers 才能决定下一步」的状态（`AGENTS.md:105`），模型容易直接跳到 approve 而不读评审证据。

### ② 模型「口头宣布通过」，绕过状态写入（最严重）

- **约束位置**：`README.md:27`「不是 prompt 里说'已经通过了'就算通过」；`README.md:548`「不得通过 prompt 文案隐式推进状态」；`README.md:529`「仅有 diff stat、commit log 或口头测试结论不足以通过质量门」。
- **IDE 中的漂移表现**：
  - 模型输出「代码评审通过 ✅，可进入下一步」，却没真正写 `review-annotations/code.yml` 的 `verdict=pass`、没写 `test-report.md`、也没调用 `approve-code` / `cr-status-set`。
  - pipeline JSON 里的 `reviewLoop`/`passCondition`（`pipeline-templates/code-implementation.pipeline.json:113-125, 174-189`）是给**平台编排器**读的机器约束。IDE 里没有编排器执行它们，模型只是「看着 JSON 假装遵守」。
  - 结果：状态机被口头推进，traceability、test-report、review annotations 出现空洞。

### ③ git 脱离 controlled-shell

- **约束位置**：`skills/shared/controlled-shell/SKILL.md:19, 84-90` 白名单化 git 子命令并**禁止**输出「请在终端手工运行」；`AGENTS.md:124`、`README.md:553` 要求 git 必须走它。
- **IDE 中的漂移表现**：
  - controlled-shell 依赖 Tauri `runGit()` 或 opencode `session.shell` 适配器（`SKILL.md:54-60`），**这些适配器在纯 Codex/Claude/Cursor/Kimi 里不存在**。
  - 模型要么用 IDE 自由终端跑任意 git（违反白名单、可能污染主工作区而非 CR worktree，`README.md:554`），要么退回被明令禁止的「请在终端运行 git…」文本。两条都是漂移。
  - `push-progress` 要求覆盖 CR workspace 下**全部**参与仓库（`pipeline...json:135`），自由 git 下模型常只 commit 文档、忘了代码仓，checkpoint 残缺。

### ④ 缺「知识库 + pipeline 执行约束层」这个地基

- **约束位置**：`README.md:11`（渐进加载、pipeline 执行约束）；`README.md:31, 33`（`specs/` + `delivery/` 是回写后的知识库，协作从「人脑记上下文」转成「CR/知识库维护上下文」）。
- **IDE 中的漂移表现**：
  - 没有知识库承接回写，`feature-writeback` 的产物（traceability.yml、specs、delivery）没有稳定落点，下一轮/下一个人接手时无从恢复上下文，只能重新脑补。
  - 没有 pipeline 执行约束层，`agent-skill-matrix.yml` 里的 owns/can-call/forbidden 边界（`AGENTS.md:59`）、node 顺序、reviewLoop replayNodes 全靠模型自觉，实际会跳节点、调用未授权 Skill、跳过 review-*/approve-*。

## 3. 核心原理：权威 / 判断 / 强制力，三者分开

用代码替换提示词约束，必须先分清三件事：

| 维度 | 能否代码化 | 说明 |
|---|---|---|
| **权威（authority）** | ✅ 能 | 「真正的状态」只能被代码改。模型再怎么口头宣布，只要权威状态（ledger）只认代码写入，口头漂移就从「结构性错误」降级成「无害的废话」 |
| **判断（judgment）** | ❌ 不能 | 代码能查「证据是否存在、形状是否正确」，查不出「评审是否真的读懂 diff、测试报告是否属实」。这部分永远留给模型 |
| **强制力（enforcement）** | ⚠️ 分环境 | Claude Code 有 hooks → 可事前硬拦截；其余 IDE 只能「CLI 唯一合法路径 + gate 事后否决」 |

> **关键思路：不要试图阻止模型「嘴上说通过」——那是 token 生成，代码管不住；而是让「真正的状态」只能被代码改。**

## 4. 提示词约束 → 代码约束对照表

| 漂移点 | 现在（提示词） | 代码替换方案 | 残留（代码替换不了） |
|---|---|---|---|
| ① 指针丢失 | AGENTS 要求「每次先读 _backlog.yml」 | `crctl status <cr>` 确定性读文件并输出指针；模型不许自报 status | 模型仍需「选择去调用」它（靠 hook/runner 兜底） |
| ② 口头宣布通过 | README「不得隐式推进」 | 把 `passCondition` 变成代码：`crctl advance` 校验不过就非零退出、拒绝写状态 | 证据的**真伪与质量**——代码只校验存在与形状 |
| ③ git 脱离白名单 | SKILL 白名单 + 禁手工指引 | PreToolUse hook deny 非包装器 git；包装器是唯一合法写入者 | 无 hook 的 IDE 只能事后 gate 否决 |
| ④ 缺执行约束层 | 靠模型自觉按 JSON 走 | runner 按 node 顺序驱动 + 校验 reviewLoop/passCondition；知识库=确定性落盘目录 | node 产物的语义质量 |

## 5. 详细优化方案

### 5.1 总体架构：三个代码组件 + 分层强制

```text
┌─────────────────────────────────────────────────────────────┐
│  模型（IDE 中的 Codex/Claude/Cursor/Kimi/Qoder）              │
│  - 负责：判断、生成、叙述                                       │
│  - 不再拥有：直接改状态文件、自由跑 git 的权力                  │
└───────────────┬─────────────────────────────────────────────┘
                │ 只能通过以下代码路径操作权威状态
                ▼
┌─────────────────────────────────────────────────────────────┐
│  组件 A: crctl  —— 状态机 gate CLI（跨所有 IDE 通用，收益最大）  │
│    · status  读 _backlog.yml + state_machine，输出确定性指针     │
│    · advance 校验转换合法性 + 校验产物达标，过则写状态并 commit  │
│    · gitwrap controlled-shell 的 IDE 等价实现（git 白名单）      │
├─────────────────────────────────────────────────────────────┤
│  组件 B: hooks  —— 逃生口硬拦截（Claude Code 强，其余降级）      │
│    · 拦 Bash 里的裸 git → 只准走 crctl gitwrap                  │
│    · 拦 Write/Edit 直接改受控状态文件 → 只准走 crctl            │
├─────────────────────────────────────────────────────────────┤
│  组件 C: pipeline-runner —— 按 JSON 驱动 + 校验 passCondition   │
│    · 按 node 顺序执行，reviewLoop 不过不进 human_approval        │
└───────────────┬─────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────┐
│  权威状态（唯一事实源，只被 crctl 写）                          │
│  _backlog.yml · cr.md · approval.yml · review-annotations/*     │
│  · test-report.md · traceability.yml · specs/ · delivery/       │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 组件 A：`crctl` —— 状态机 gate CLI

把 `cr-status-set` 从「模型执行的 Skill」变成「模型调用的代码」。这是收益最大、跨所有 IDE 通用的一步，直接治理 ①②③。

**技术选型建议**：Node.js 单文件 CLI（本包 `skills/shared/engineering-docs/scripts/` 已用 TS/Node，生态一致；也可编译为无依赖单文件便于各 IDE 调用）。

**子命令设计**：

| 子命令 | 输入 | 行为（全部确定性代码） | 治理 |
|---|---|---|---|
| `crctl status <cr_id>` | CR-ID | 读 `_backlog.yml` 定位条目，读 `dir-graph.yaml#state_machine`，输出 `CR-ID / status / 来源文件+hash / 合法的下一步 trigger 列表 / 缺失产物清单` | ① |
| `crctl advance <cr_id> --to <status> --trigger <t>` | 目标状态、触发器 | ①校验 `(current,next,trigger)` 在 `transitions[]`（支持 `any-active` wildcard）；②校验目标状态所需产物存在且字段达标；③全过才写 `_backlog.yml` + `cr.md` frontmatter 并 commit，否则非零退出+结构化错误，**不写** | ①② |
| `crctl gate <cr_id> --for <status>` | 目标状态 | 只校验不写：返回该状态门禁的 `pass/block` 与缺失项（供 runner 与人工预检） | ② |
| `crctl git <sub> [args] --cwd <path>` | git 子命令 | controlled-shell 白名单的 IDE 实现：只放行 `SKILL.md:25-45` 中列出的子命令，越界返回 `FORBIDDEN_SUBCOMMAND`；每次调用打审计日志 | ③ |

**门禁校验规则（passCondition 代码化，对齐 pipeline JSON）**：

```text
advance → code-approved 必须同时满足（对齐 code-implementation.pipeline.json:174-189）：
  - review-annotations/code.yml.verdict == "pass"
  - review-annotations/code.yml.blockers == []
  - test-report.md 存在 且 status == "pass"
  - traceability.yml#tests 段非空
  - test-report.md.tester 与 cr.md.owners.test.id 一致（否则要求记录偏差原因）

advance → requirement-approved 必须：
  - review-annotations/requirement.yml.verdict == "pass" 且 blockers == []

advance → tech-design-reviewed 必须（对齐 AGENTS.md:105）：
  - review-annotations/sdd.yml.verdict == "pass" 且 blockers == []
```

**防手改兜底（无 hook 的 IDE 也能守住权威）**：
`crctl advance` 写状态 commit 时附带一个只有它能算出的 trailer，例如：

```text
[cr] status CR-2026-001 developing -> code-reviewing

X-crctl-token: <HMAC(secret, cr_id + from + to + tree_sha)>
```

`crctl advance` 在推进前校验历史状态 commit 的 token 链；裸 git 手改的 commit 没有合法 token → **拒绝推进**。这样即使某个 IDE 拦不住执行，漂移也无法在 gate 处蒙混过关。secret 存目标 workspace 的本地配置（不入库、不硬编码，遵守 `AGENTS.md:159` 禁绝对路径/禁硬编码）。

### 5.3 组件 B：hooks —— 逃生口硬拦截

**Claude Code（能力最强，事前硬拦截）**：在目标 workspace 的 `.claude/settings.json` 配置：

- `PreToolUse` on `Bash`：正则匹配 `\bgit\b`，若不是 `crctl git …` 形式 → `deny`，并提示改用 `crctl git`。
- `PreToolUse` on `Write`/`Edit`：目标路径命中 `change-requests/**/_backlog.yml`、`**/cr.md`(status 字段)、`**/approval.yml`、`**/review-annotations/*.yml` → `deny`，提示改用对应 `crctl` / `approve-*` Skill。

> 本包已收录 `git-guardrails-claude-code` 技能思路可复用；本方案是其「状态文件 + git 双拦截」的定制版。

**其余 IDE（Codex/Kimi/Cursor/Qoder，降级策略）**：
- 若该 IDE 提供 hook/tool-gate 机制 → 等价配置。
- 若没有 → 依赖 5.2 的 **token 兜底**：拦不住执行，但 `crctl` 在 gate 处否决非法来源的状态变更；同时在 workspace 的 `AGENTS.md` 顶部加一段「本环境无 hook，git 一律走 `crctl git`」的醒目约束（提示词兜底，作为最后一道）。

### 5.4 组件 C：`pipeline-runner` —— 按 JSON 驱动

把 pipeline JSON 从「模型阅读的说明」变成「代码执行的脚本」，治理 ④。

- 读 `pipeline-templates/{flow}.pipeline.json`，按 `nodes[]` 顺序推进。
- 每个 `kind:skill` 节点执行后，调用 `crctl gate` 校验该节点声明的产物。
- 遇到含 `reviewLoop` 的节点：`passCondition` 不满足时，严格按 `replayNodes[]` 顺序回修（`pipeline...json:100-111, 151-172`），`maxAttempts` 用尽才停；**blocker 未清空绝不进入 `human_approval`**。
- `human_approval` 节点：runner 暂停，等待外部确认信号（人工在 CLI/UI 点通过），随后必须调用显式 `approve-*` 节点写状态——不允许 runner 自己推进（对齐 `AGENTS.md:109`）。

**最小可用形态**：先不做全自动 runner，做一个 `crctl next <cr_id>` —— 读当前 status + 产物，输出「下一个该跑的 node.ref 及其入参」。这已能挡住「跳节点」，实现成本远低于全量 runner。

### 5.5 知识库落点

pipeline 执行约束层需要稳定的回写落点，否则 `feature-writeback` 产物无处安放（漂移根源之一）。在目标 workspace 固定：

- `specs/{id}/`：回写后的 PRD/SDD baseline（只由 `writeback-prd-sdd` 写，`README.md:546`）。
- `delivery/task/`：回写后的任务。
- `traceability.yml`：需求↔设计↔任务↔测试↔代码提交的追溯链。

`crctl advance → archived` 前校验以上落点已生成，未生成则否决——把「知识库有没有真正沉淀」也变成代码门禁。

## 6. 分阶段落地路线图

| 阶段 | 交付物 | 治理漂移点 | 依赖 | 优先级 |
|---|---|---|---|---|
| P1 | `crctl status` + `crctl advance` + `crctl gate`（含 passCondition 代码化 + token 兜底） | ①② | 无 | 最高（跨 IDE 通用、收益最大） |
| P2 | `crctl git`（controlled-shell 的 IDE 实现，白名单） | ③ | P1 | 高 |
| P3 | Claude Code hooks（git + 状态文件双拦截） | ③（硬拦截） | P2 | 高（仅 Claude Code） |
| P4 | `crctl next`（最小 runner） | ④（防跳节点） | P1 | 中 |
| P5 | 完整 `pipeline-runner`（reviewLoop/replayNodes 自动回修） | ④ | P4 | 中 |
| P6 | 知识库落点门禁（archived 前校验 specs/delivery/traceability） | ④ | P1、P5 | 中 |

**建议起步顺序：P1 → P3 → P2 → P4**。P1 先把「权威」搬进代码（最关键）；P3 在 Claude Code 里立刻拿到硬拦截；P2 补齐跨 IDE 的 git 通道；P4 挡跳节点。

## 7. 诚实的边界（永远留给模型 + 提示词）

1. **证据的真伪与质量**：代码能查 `code.yml` 有没有 `verdict=pass`、diff range 是否非空、引用文件是否存在；查不出「评审是否真读懂 diff」。可抬高门槛逼近（要求 diff hash 与 worktree 实际 diff 一致、捕获测试命令原始输出、要求覆盖率数字），但到不了 100%。
2. **口头 prose 本身**：模型仍会输出「✅ 已通过」。代码不 gag 它，只让它**不算数**。
3. **跨 IDE 强度不均**：Claude Code 能硬拦截；其余只能「CLI 唯一合法路径 + gate 事后否决」。这是环境决定的。

---

## 8. 验收标准

治理生效的可验证信号：

- [ ] 任意时刻 `crctl status <cr>` 输出的 status 与 `_backlog.yml` 完全一致，模型不再自报 status。
- [ ] 在缺失 `code.yml.verdict=pass` 或 `test-report.status=pass` 时执行 `crctl advance --to code-approved` **必定非零退出且不写文件**。
- [ ] 裸 git 手改状态 commit 后，`crctl advance` 因 token 校验失败而拒绝推进。
- [ ] Claude Code 环境下，`git commit` 直接调用被 hook deny，只有 `crctl git` 放行。
- [ ] `crctl next` 在 `review-annotations` 有未清 blocker 时，绝不返回 `human_approval` 作为下一步。
- [ ] `crctl advance --to archived` 在 `specs/`/`delivery/`/`traceability.yml` 未生成时否决。

## 附：与现有约束的关系

本方案**不改动**任何现有 Skill / Pipeline / `_index.yml` / `agent-skill-matrix.yml` 的契约，是在其之上补一个**执行强制层**：

- `crctl advance` 是 `cr-status-set`（`skills/cr/cr-status-set/SKILL.md`）的代码化执行器，校验规则与其 `操作步骤` 一致。
- `crctl git` 是 `controlled-shell`（`skills/shared/controlled-shell/SKILL.md`）在 IDE 环境的运行时适配器实现（对应 `SKILL.md:106-111` 的「运行时适配要求」）。
- `pipeline-runner` 执行的就是 `pipeline-templates/*.pipeline.json`，不新增编排语义，只强制其被真实执行。

即：**把已有的提示词契约，配一个代码执行者。**
