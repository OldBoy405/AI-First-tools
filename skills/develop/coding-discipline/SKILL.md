# Skill: coding-discipline

**类型**: 开发期 Skill（develop/ 组，纪律兜底事实源）
**调用时机**: implement-code 执行 TASK 与自修复时遵循；write-dev-plan 引用 §2 粒度约束

---

## §1 极简阶梯（选方案）

按序停在第一个成立的台阶：

1. 需要存在吗？投机性需求 = 不做（YAGNI）。
2. 代码库已有？helper / util / 类型 / 既有模式 → 复用，先看再写。
3. 标准库能做？用它。
4. 平台原生能力覆盖？原生优先于依赖。
5. 已安装的依赖能解？用它，不为几行代码能做的事新增依赖。
6. 能一行写完？一行。
7. 以上皆否：最小可用实现。

信任边界校验、防数据丢失的错误处理、安全措施、可访问性基础**不在精简范围内**。

## §2 执行步骤粒度

单 TASK 内部步骤按 2-5 分钟切分：写验证用例 → 跑到失败/明确当前状态 → 实现 → 复验 → 提交。每步含精确文件路径与验证步骤，禁止 TBD/占位符。TASK 本身粒度（1-3 天）由 write-dev-tasks 定义，不受本节约束。

## §3 根因排查 + 回归验证

- 自修复模式（review_feedback 存在）动手前先定位根因：哪个 TASK、哪一行、什么假设不成立；同一根因下所有失败点一次修完。节点输出必须含 root-cause 字段（与 fixed-blockers 并列）。
- 修复针对 bug 时回归测试先验红（临时还原修复前代码确认失败）再验绿（恢复修复确认通过），两次结果写入节点输出。
